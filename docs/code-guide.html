코드 기여 가이드

문서 링크를 고쳐 봤다면 다음은 코드입니다. Chromium에는 처음 오는 사람도 할 수 있는 정리 작업이 많습니다. 아래 순서대로 한 단계씩 올라가는 것을 권합니다. 2단계부터는 Chromium 전체를 받아 빌드해야 하므로 집에서 합니다.

난이도 순서#

단계 할 일 확인 방법 동작 변화 리뷰에서 필요한 것
1 문서 링크 고치기 링크 눌러 보기 없음 커미터 누구나
2 안 쓰는 include, 만료된 NotFatalUntil 인자 지우기 컴파일 없음 그 폴더 OWNERS
3 헤더·API 교체 빌드와 단위 테스트 같은 결과가 나와야 함 폴더 OWNERS와 API 담당자
4 만료 히스토그램 지우기 빌드와 XML presubmit 사용자에게 안 보임 그 지표 담당자
5 만료된 kill switch·flag 지우기 빌드와 테스트 켜진 동작으로 굳어짐 기능 담당자의 출시 완료 확인
6 수명과 동작을 따지는 수정 직접 설계한 테스트 바뀜 멘토와 일대일로

가장 큰 벽은 1단계에서 2단계로 넘어갈 때입니다. 여기서부터 전체 체크아웃과 빌드가 필요합니다. 2단계와 3단계는 코드 카드 10장으로 바로 해 볼 수 있습니다.

공통 준비#

  • 받기와 빌드 준비: 코드 카드 안내 1단계에 운영체제별 공식 안내와 빠르게 빌드하는 gn args가 있습니다.
  • 빌드와 테스트: 바꾼 파일이 들어 있는 테스트 타깃을 빌드하고, 그 테스트만 골라 돌립니다.
gn refs out/Default //net/cert/cert_verify_proc.cc   # 이 파일을 쓰는 타깃 찾기
autoninja -C out/Default net_unittests
out/Default/net_unittests --gtest_filter='CertVerifyProc*'
autoninja -C out/Default ../../net/cert/cert_verify_proc.cc^   # 파일 하나만 컴파일
  • 올리기 전: git cl format으로 모양을 맞추고, 바꾼 코드를 지나는 테스트가 통과하는지 봅니다.

단계별로 일감 찾기#

2단계. 안 쓰는 include, 만료된 NotFatalUntil#

  • include: 진행 중인 이전 작업에서 남은 파일을 찾습니다. 예를 들어 crypto/hash 이전(이슈 372283556)에서 옛 헤더만 남은 파일이 코드 카드 C1~C5입니다.
  • NotFatalUntil: CHECK(조건, base::NotFatalUntil::M152)는 M152부터 이미 크래시하는 CHECK라 인자만 남은 상태입니다. 지금 main의 마일스톤은 chrome/VERSION의 MAJOR로 봅니다(10월 29일 기준 159).
git grep -n "NotFatalUntil::M15[2-8]" -- '*.cc' '*.h'
  • base에 정리 스크립트(base/tools/clean-up-not-fatal-until.py -m <M>)가 있고 base OWNERS가 가끔 한꺼번에 지웁니다. 폴더 하나를 골라 git log로 최근 정리와 겹치지 않는지 보고 그 폴더만 정리합니다.
  • 예: 8264232 include 지우기, 8377550 quota CHECK의 M148 인자 지우기.

3단계. 헤더·API 교체#

  • 옛 API를 새 API로 옮기는 버그를 따라갑니다. 예: crypto/hash 이전(372283556), sql::Statement 시간 접근자(40176243). 버그에 붙은 머지된 CL을 보면 바꾸는 법이 정해져 있습니다.
  • 바꾼 뒤에도 결과가 같다는 것을 테스트로 확인하고, 저장 형식이나 값이 바뀌지 않는 이유를 커밋 메시지에 씁니다.
  • 예: 8474691 손으로 하던 시간 변환을 ColumnTime()·BindTime()으로 교체.

4단계. 만료 히스토그램#

  • 히스토그램은 histograms.xml의 expires_after가 지나면 기록하는 코드가 죽은 코드가 됩니다. 히스토그램 README에 만료되면 기록 코드를 지우고 XML도 정리하라고 적혀 있습니다.
git grep -nE 'expires_after="(M1[0-4][0-9]|202[0-4]-)' -- tools/metrics/histograms/metadata/   # 오래전에 만료된 것
  • 일부러 만료시켜 두고 코드를 남긴 것은 XML에 표시가 있으니 건너뜁니다. 기록하는 코드, XML 항목, 그 히스토그램만 쓰던 enum을 함께 지웁니다.
  • 예: 8505716 만료된 Arc.NearbyShare 히스토그램 6개 지우기.

5단계. 만료된 kill switch·flag#

  • kill switch는 새 동작을 켜 두면서 문제가 생기면 끌 수 있게 남긴 스위치입니다. 정해 둔 마일스톤이 지나고 기본값으로 켜져 있으면 스위치를 지우고 켜진 동작만 남깁니다.
  • "M1xx 뒤에 지운다" 같은 주석이나, chrome/browser/flag-metadata.json에서 expiry_milestone이 지난 flag를 찾습니다. flag를 지우는 법은 flag 만료 문서에 있습니다.
git grep -nEi '(remove|delete)[^.]{0,40}(after|once|in|by) M1[0-5][0-9]' -- '*.cc' '*.h'
  • 지우기 전에 기능 담당자에게 출시가 끝났는지 먼저 묻습니다. 서버 쪽 실험으로 아직 끄고 있을 수 있어서, 밖에서는 알 수 없습니다.
  • 예: 8457502 M133 뒤에 지우기로 했던 FFmpeg kill switch 지우기.

6단계. 수명과 동작을 따지는 수정#

  • 정해진 방법이 없습니다. 호출부를 모두 읽고 불변식을 증명하거나, 오류 처리와 테스트를 직접 설계해야 합니다. 리뷰도 여러 번 오갑니다.
  • 예: 8278112 WeakPtr를 확인하던 DCHECK를 CHECK로, 8282239 QuotaDatabase를 scoped sql::Transaction으로.
  • 5단계까지 해 본 뒤 멘토와 일대일로 고르는 것을 권합니다.

커밋 메시지#

코드 CL에는 무엇을 왜 바꿨는지, 동작이 바뀌지 않는다면 그 근거를 씁니다.

[storage] Remove expired NotFatalUntil::M148 from quota CHECKs

M148 is long past, so the argument no longer has any effect.

Bug: none
  • 제목 앞의 [컴포넌트]나 폴더: 접두어는 그 폴더의 최근 커밋을 따라 씁니다. git log --oneline -- <폴더>로 봅니다.
  • 관련 버그가 있으면 Bug: <번호>, 그 CL로 버그가 끝나면 Fixed: <번호>, 없으면 Bug: none을 씁니다.

리뷰 받을 때#

  • 그 폴더의 OWNERS가 한 명 있어야 승인이 됩니다. git cl owners나 Gerrit 리뷰어 칸의 OWNERS 제안으로 찾습니다.
  • 커미터가 아니면 커미터 두 명의 +1이 필요합니다. 폴더 OWNERS 한 명과, 그 이전 작업을 이끄는 사람이나 다른 OWNERS 한 명을 넣습니다.
  • 참가자 계정은 dry run도 CQ+2도 걸 수 없으니 Start Review 메시지에 부탁합니다. 예시 문장은 코드 카드 안내 6단계에 있습니다.
  • 그 뒤 흐름은 리뷰 받기와 같습니다.
