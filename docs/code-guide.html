코드 기여 가이드

문서 기여는 docs/ 폴더만 받아 빌드 없이 올렸습니다. 코드는 Chromium 전체를 받아 빌드하고, 바꾼 코드를 지나는 테스트를 돌린 뒤 올립니다. 아래는 첫 CL 올리기와 달라지는 부분만 단계별로 적은 것입니다. 시간이 오래 걸려서 집에서 합니다.

문서 기여와 다른 점#

문서 기여 코드 기여
소스 docs/만 sparse 클론, 1분, 252MB fetch chromium으로 전체, 한두 시간, 디스크 100GB 이상
일감 이슈 카드 28장 코드 카드 10장, Issue Tracker의 GoodFirstBug 핫리스트
빌드 없음 gn args로 설정하고 autoninja로 빌드, 첫 빌드는 몇 시간
확인 링크 눌러 보기 바꾼 코드를 지나는 단위 테스트 돌리기
올리기 전 커밋 메시지 확인 git cl format, 테스트 통과
리뷰어 커미터 누구나, docs/는 OWNERS가 * 그 폴더의 OWNERS
봇 검사 presubmit 두 개 여러 운영체제에서 빌드와 테스트

0단계. 준비물#

  • 메모리 16GB 이상, 빈 디스크 100GB 이상을 권합니다(공식 안내 기준).
  • Linux와 macOS가 가장 수월합니다. Windows는 Visual Studio 2026 설치가 더 필요합니다.
  • depot_tools는 사전 준비 때 깐 것을 그대로 씁니다.
  • 행사 때 받은 src/는 문서만 받은 것이라 빌드할 수 없습니다. 새 폴더에 받습니다.
  • 막히면 운영체제별 공식 안내를 봅니다: Linux · macOS · Windows

1단계. 전체 소스 받기#

mkdir ~/chromium && cd ~/chromium
fetch --nohooks --no-history chromium   # 한두 시간 걸린다
cd src
./build/install-build-deps.sh           # Linux만, 처음 한 번
gclient runhooks
  • macOS와 Windows는 fetch --no-history chromium 한 줄로 받고 cd src로 들어갑니다. install-build-deps와 gclient runhooks는 하지 않습니다.
  • --no-history는 예전 기록을 받지 않아 시간과 디스크를 아낍니다.

2단계. 빌드 설정#

gn args out/Default   # 편집기가 열리면 아래 세 줄을 넣고 저장
symbol_level = 0
blink_symbol_level = 0
v8_symbol_level = 0

디버그 정보를 줄여 빌드를 빠르게 하는 설정입니다. 공식 안내의 "Faster builds"에 있는 방법이고, 나머지는 기본값인 디버그 빌드를 그대로 씁니다.

3단계. 빌드#

브라우저 전체가 아니라 바꿀 코드의 테스트 타깃만 빌드하면 빠릅니다.

gn refs out/Default //net/cert/cert_verify_proc.cc       # 이 파일이 들어 있는 타깃 찾기
autoninja -C out/Default net_unittests                    # 테스트 타깃 빌드
autoninja -C out/Default ../../net/cert/cert_verify_proc.cc^   # 파일 하나만 컴파일
  • 첫 빌드는 몇 시간 걸립니다. 다음부터는 바뀐 부분만 다시 빌드합니다.
  • 브라우저를 직접 띄워 보고 싶으면 autoninja -C out/Default chrome입니다. 가장 오래 걸립니다.
  • 빌드한 브라우저 실행은 Linux out/Default/chrome, macOS out/Default/Chromium.app/Contents/MacOS/Chromium, Windows out\Default\chrome.exe입니다.

4단계. 일감 고르기#

  • 처음이라면 코드 카드 10장 중 하나를 고릅니다. 바꿀 곳과 돌릴 테스트가 정해져 있습니다.
  • 그다음은 Issue Tracker의 GoodFirstBug 핫리스트에서 찾습니다. 관심 있는 컴포넌트로 좁혀 보면 고르기 쉽습니다.
  • 고른 이슈에 댓글로 작업하겠다고 밝힙니다. 그 전에 담당자(assignee)가 이미 있는지, 같은 이슈로 열린 CL이 있는지 봅니다.
  • 무엇을 고를지 막막하면 멘토와 상의합니다.

5단계. 브랜치 만들고 고치기#

git new-branch my-fix

고친 뒤에는 git cl format으로 모양을 맞춥니다. C++은 clang-format, BUILD.gn은 gn format이 알아서 돌아갑니다.

6단계. 테스트#

autoninja -C out/Default net_unittests
out/Default/net_unittests --gtest_filter='CertVerifyProc*'
  • 바꾼 코드를 지나는 테스트를 골라 돌립니다. 테스트 이름은 같은 폴더의 *_unittest.cc에서 TEST_F(이름, …)를 보면 나옵니다.
  • 브라우저를 띄우는 테스트는 browser_tests, content_browsertests처럼 따로 있고 더 오래 걸립니다.
  • 모두 통과해야 올립니다.

7단계. 커밋과 업로드#

git commit -a
git cl upload -f --hashtag=hacktoberfest-seoul-2026
  • 커밋 메시지 양식은 첫 CL 올리기 4단계와 같습니다. 본문에는 무엇을 왜 바꿨는지, 동작이 바뀌지 않는다면 그 근거를 씁니다.
  • 제목 앞의 [컴포넌트]나 폴더: 접두어는 그 폴더의 최근 커밋을 따라 씁니다. git log --oneline -- <폴더>로 봅니다.
  • 관련 버그가 있으면 Bug: <번호>, 그 CL로 버그가 끝나면 Fixed: <번호>, 없으면 Bug: none을 씁니다.
  • 첫 기여라면 AUTHORS에 이름을 넣습니다.

8단계. 리뷰 요청#

  • 그 폴더의 OWNERS가 한 명 있어야 승인이 됩니다. git cl owners나 Gerrit 리뷰어 칸의 OWNERS 제안으로 찾습니다. 커미터가 아니면 커미터 두 명의 +1이 필요합니다.
  • 코드 CL은 봇이 여러 운영체제에서 빌드와 테스트를 돌려 봐야 합니다. 참가자 계정은 dry run도 CQ+2도 걸 수 없으니 Start Review 메시지에 부탁합니다.
I don't have try job access, so could you start a CQ dry run, and
Submit to CQ once it's approved?
  • dry run에서 다른 운영체제 빌드나 테스트가 깨지면 고쳐서 새 패치셋을 올립니다. 그 뒤 흐름은 리뷰 받기와 같습니다.

소스를 최신으로 맞추기#

며칠 지나 다시 작업할 때는 먼저 이 두 줄을 돌리고 다시 빌드합니다.

git rebase-update   # main을 받아 내 브랜치를 그 위로 옮긴다
gclient sync        # 의존 저장소도 맞춘다
